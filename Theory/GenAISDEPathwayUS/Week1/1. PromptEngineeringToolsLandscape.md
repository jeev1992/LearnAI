# Prompt Engineering Tools Landscape: Read-Aloud Class Script

This slide is showing us the emerging landscape of LLM application architecture.

The easiest way to read this image is to focus on the two axes first.

As we move to the right, flexibility increases.

As we move upward, complexity increases.

So this chart is really telling us that as LLM systems become more flexible, they usually also become more complex to build, test, and operate.

That is the main idea I want you to keep in mind while we walk through the slide.

This is not a slide about memorizing tool logos.

It is a slide about understanding how LLM applications evolve.

Most teams do not start on the far right.

Most teams start on the left with something simple, and then they move right only when the problem demands more capability.

So let us walk through this landscape from left to right.

## Level 1: Static Prompts

At the beginning, we have static prompts.

This is the simplest form of using an LLM.

You write an instruction.

You send it to the model.

The model gives you a response.

There is no memory.

There is no retrieval.

There is no multi-step workflow.

It is just one prompt and one response.

This is how most people first experience systems like ChatGPT.

**Intuition:** This is where everyone starts. There is no infrastructure. No pipelines. No system. Just you and the model, one conversation at a time. It is immediate and interactive.

**Examples:**
- Explain this quantum computing concept
- Summarize this paragraph
- Rewrite this email in a more professional tone
- Translate this sentence to Spanish
- Generate a creative story title
- Debug this code snippet

**Real-world use cases:**
- A student using ChatGPT to understand a topic
- A content writer asking for title suggestions
- A developer asking for help understanding an error message
- A non-native speaker getting translation help

Static prompts are useful for experimentation, learning, and fast prototyping.

But they do not scale very well.

If the task changes, the prompt often has to be rewritten manually.

## Level 2: Prompt Templates

The next step is prompt templates.

Now instead of writing a new prompt every time, we create a reusable prompt with placeholders.

**Intuition:** Once you realize you are asking the same question repeatedly but with different data, you upgrade to templates. This is automation thinking. Write once, reuse many times.

**Examples:**
- Template: Summarize the following text in three bullet points: [TEXT]
- Template: Classify this customer email as urgent, normal, or low-priority. Email: [EMAIL_TEXT]
- Template: Extract the price from this product description: [PRODUCT_DESCRIPTION]
- Template: Generate a social media caption for this image topic: [TOPIC]

**Real-world use cases:**
- A customer service system that classifies incoming tickets with the same prompt structure but different ticket content
- A marketing tool that generates product descriptions from a consistent template
- A data extraction pipeline that pulls information from hundreds of resumes using the same prompt structure
- A chatbot that responds to common categories of questions with templated prompts

This is an important step because it moves us from one-off prompting into reusable prompt design.

Templates are useful when the instruction stays the same but the data changes.

So if static prompts are like writing one email by hand, templates are like creating a reusable form.

But templates still do not solve deeper problems like memory, retrieval, or complex reasoning.

## Level 3: Prompt Composition

After prompt templates, we move into prompt composition.

This is where prompts stop being isolated and start becoming components.

Instead of one prompt doing everything, we build a flow of smaller prompt modules.

One prompt might extract data.

Another might classify intent.

Another might generate the final answer.

This is useful because real business tasks are rarely a single instruction.

They are usually pipelines.

**Intuition:** You realize that hard problems are actually sequences of simpler problems. Instead of writing one giant prompt that tries to do everything, you break it into smaller, specialized prompts that are easier to test, debug, and improve.

**Example: Customer Support Ticket Workflow**
- Step 1 prompt: Extract the customer issue from the ticket
- Step 2 prompt: Determine urgency level (critical, high, medium, low)
- Step 3 prompt: Route to the appropriate department
- Step 4 prompt: Draft an initial response
- Step 5 prompt: Add internal notes for the support team

**Real-world use cases:**
- Insurance claim processing: Extract claim info → Validate policy → Calculate payout → Generate letter
- Hiring pipeline: Parse resume → Extract experience level → Match job criteria → Score candidate → Generate feedback
- Content moderation: Classify content → Check policies → Flag if needed → Generate reason for moderation decision
- Loan application: Extract financial data → Check credit score → Calculate risk → Generate approval/denial letter

So at this stage, we are no longer just writing prompts.

We are designing systems made of prompt components.

## Level 4: Contextual Prompts

Next we move into contextual prompts.

This is a big step.

Now the model does not just see the user’s latest message.

It also sees supporting context.

That context might be conversation history.

It might be a user profile.

It might be previous outputs.

It might be business metadata.

It might be documents.

**Intuition:** The model is now aware of its own history and the user's background. This is where systems start to feel intelligent, not because the model changed, but because it has more information to work with.

This is where AI systems start to feel smarter in a practical sense.

Not necessarily because the model itself changed.

But because the system is feeding it better context.

**Examples:**
- User says: Write a follow-up email
  - Without context: System writes a generic follow-up
  - With context: System sees previous email thread, tone preference, relationship history, and writes the perfect follow-up
- User asks: What should I do next?
  - Without context: System gives generic advice
  - With context: System knows user's project status, past decisions, constraints, and gives specific recommendations
- Customer inquiry: Can I return this?
  - Without context: Generic return policy
  - With context: System sees purchase date, item category, return history, and gives personalized answer

**Real-world use cases:**
- Chatbots that remember your preferences across conversations
- Email assistants that know your writing style and recipient relationships
- Coding assistants that understand your codebase and recent changes
- HR systems that know employee history, performance, and compensation context

So one important line to remember is this.

A prompt by itself is often not enough.

A prompt plus the right context is much more powerful.

But contextual prompting has its own challenge.

Bad context can be worse than no context.

Too much irrelevant information confuses the model and increases cost.

## Level 5: Prompt Chaining

After contextual prompts, we arrive at prompt chaining.

This means one model call feeds the next.

The output of one step becomes the input to another step.

This is how we handle multi-step tasks in a structured way.

**Intuition:** Instead of asking the model to do everything at once, you ask it to solve step-by-step, using its own output as input for the next step. This breaks down reasoning into digestible chunks.

**Example: Meeting Processing Pipeline**
- Step 1: Summarize the meeting transcript
- Step 2 (uses Step 1): Extract action items from the summary
- Step 3 (uses Step 2): Assign owners to each action item
- Step 4 (uses Step 3): Draft a follow-up email with assignments
- Step 5 (uses Step 4): Schedule reminder notifications

**Real-world use cases:**
- Document analysis: Extract key facts → Identify risks → Recommend actions → Generate report
- Customer inquiry: Classify issue → Find relevant policy → Generate response → Escalate if needed
- Research: Gather information → Organize findings → Write outline → Generate full article → Create summary
- Code review: Analyze code → Identify issues → Suggest fixes → Generate review comment

One helpful distinction is this.

Composition is about modular design.

Chaining is about ordered execution.

They are related, but they are not exactly the same.

Chaining makes systems more capable, but it also introduces more latency, more failure points, and more evaluation work.

## Level 6: RAG / Prompt Pipelines

Now we come to one of the most important parts of the slide.

Retrieval-augmented generation, or RAG, and prompt pipelines.

This is the area where many production-grade enterprise systems actually live.

**Intuition:** The model no longer relies only on what it learned during training. It now searches for current, relevant knowledge and uses that as ground truth. This is the difference between knowing something and looking it up.

This is why I want you to pay close attention to the black diagonal labeled vector embeddings and semantic search.

That line marks a major shift.

Before this point, the system is mostly relying on prompt design and workflow structure.

After this point, the system starts to retrieve knowledge from external sources.

That means the model is no longer limited to only what it remembers from training.

Now it can search manuals, policies, documents, knowledge bases, and other data sources at runtime.

Then it can inject that information into the prompt and answer from evidence.

This is why RAG became such an important architecture pattern.

It allows us to ground answers in real content.

It also makes LLM systems much more useful in enterprise settings.

**Examples:**
- Chat with your documents: User uploads a PDF and asks questions. System retrieves relevant pages and answers from them.
- Policy assistant: Employee asks about vacation policy. System searches company policy database, retrieves relevant section, and answers accurately.
- Customer support copilot: Customer asks about a product. System searches product documentation, warranty info, FAQ, and past tickets, then provides accurate support.
- Legal research: Lawyer searches for precedents. System searches case database, retrieves similar cases, and summarizes relevant rulings.

**Real-world use cases:**
- Internal knowledge bots: Employees search company procedures, past projects, lessons learned
- Medical research: Doctors search medical journals and case histories to answer clinical questions
- Technical support: Support reps search documentation, ticket history, and troubleshooting guides
- Financial advisors: Advisors search market data, regulations, and client history for personalized recommendations

This is also the point where prompt engineering becomes knowledge engineering.

Now we care about chunking.

We care about indexing.

We care about embedding quality.

We care about retrieval ranking.

We care about grounding.

We care about citations.

We care about prompt injection and source trust.

And there is one important warning here.

RAG does not magically solve hallucinations.

If retrieval is poor, the answer will still be poor.

So RAG improves grounding, but only when retrieval quality is good.

## Level 7: Autonomous Agents

After RAG, the chart moves toward autonomous agents.

This is another major jump.

**Intuition:** For the first time, the system can decide what to do next on its own. Instead of following a pre-written script, it reasons about the goal, considers options, and chooses its actions. This is delegation. Most agents work using a pattern called ReAct: the agent Reasons about what to do, Acts by calling a tool, Observes the result, and repeats until the goal is met.

An autonomous agent is not just answering a question.

It is deciding what to do next.

It may plan a sequence of steps.

It may call tools.

It may inspect results.

It may store memory.

It may revise its path based on what happens.

So if prompt chaining is a fixed workflow, an agent is a workflow that can make some of its own decisions.

That is why agents are so flexible.

But that is also why they are harder to control.

**Examples:**
- Data analysis agent: User says analyze this dataset. Agent reasons: I should load the data, check for missing values, then visualize. It acts by running code, observes the results, and decides the next step.
- Research agent: User asks for competitive research. Agent thinks: I should search for competitor info, extract key points, compare strategies. It searches, reads, extracts, observes findings, and decides what else to research.
- Travel planning agent: User says I need a trip to Europe. Agent reasons: I should search destinations, check prices, verify availability. It calls search tools, observes pricing, reasons about trade-offs, and continues planning.
- Troubleshooting agent: System reports a bug. Agent thinks: I should log this, reproduce the error, check logs. It takes actions, observes results, reasons about likely causes, and decides whether to fix or escalate.

**Real-world use cases:**
- IT operations: Agents detect system issues, reason about causes, call diagnostic tools, observe system state, and apply fixes
- Recruitment: Agents screen resumes (act), reason about fit, conduct interviews (act), observe candidate quality, compile reports
- Financial analysis: Agents reason about market signals, gather data (act), analyze trends, observe patterns, recommend actions
- Scientific research: Agents reason about hypotheses, design experiments (act), collect data, observe results, propose next steps

For example, if I ask the system to analyze a dataset, identify the largest performance drop, explain likely reasons, and draft a manager update, that is more agentic because the system has to decide how to execute the task.

Agents are powerful, but they are often overused.

Many problems that people call agent problems are really better solved with deterministic chains or RAG-based workflows.

So one important teaching point is this.

Do not use an autonomous agent where a fixed workflow would be safer, cheaper, and easier to evaluate.

## Level 8: Prompt Tuning / Soft Prompts

Finally, at the far right, we reach prompt tuning and soft prompts.

This is where the conversation moves closer to model adaptation.

**Intuition:** You stop editing the text of your prompts and start letting the model learn how to steer itself. Instead of writing instructions, you optimize embeddings that influence the model's behavior.

Up to this point, we have mostly been changing the system around the model.

We changed the wording.

We changed the structure.

We changed the context.

We changed the retrieval layer.

We changed the workflow.

Now we start changing how the model itself is steered.

Here is the simplest way to explain this section in class.

Earlier levels use prompts that humans can read and write.

Soft prompting uses learned representations that influence the model, even if a human cannot read them as plain language instructions.

A simple mental model is this.

Hard prompts are like instructions you write on a whiteboard for the model to read.

Soft prompts are like hidden control knobs that are adjusted so the model behaves better on a task.

So static prompts and templates are human-written steering.

Soft prompts are machine-learned steering.

**Examples:**
- Insurance claim classification: Train soft prompt on thousands of claims to perfectly classify claim types
- Legal document review: Learn soft prompt that helps model spot risky clauses specific to your contracts
- Medical diagnosis: Tune soft prompt on your hospital's patient data to better diagnose conditions in your population
- Customer support tone: Optimize soft prompt so model matches your brand voice perfectly

**Real-world use cases:**
- Insurance: Route claims to correct department with domain-specific soft prompt trained on company data
- Legal: Specialize model for contract review by tuning soft prompt on your firm's historical cases
- Healthcare: Adapt model for your patient population and clinical protocols with task-specific soft prompt
- Finance: Customize credit risk assessment with soft prompt trained on your loan portfolio
- Customer service: Specialize model to match your exact tone and brand with company-specific soft prompt

This is also where students often confuse prompt tuning with fine-tuning.

So make the distinction clearly.

In full fine-tuning, we update many model parameters.

In prompt tuning, we usually keep the big model frozen and learn a much smaller prompt-like embedding that conditions the model for a task.

So both are adaptation techniques.

But prompt tuning is often lighter-weight than full fine-tuning.

A good example would be a narrow enterprise classification problem.

Imagine routing insurance claims.

Or categorizing legal requests.

You might begin with prompt engineering.

But if that stops being enough, and you have task data, prompt tuning becomes interesting because you can specialize the system without retraining the full model.

This is why prompt tuning sits at the far right.

It offers a lot of power, but it also requires more ML maturity.

Now we are talking about embeddings, optimization, evaluation, task data, and parameter-efficient adaptation.

So this is not where most product teams should begin.

Most teams should first become very strong at prompt design, context engineering, retrieval, and workflow orchestration.

The message is not that everyone should go do prompt tuning.

The real message is that when human-written prompts are no longer enough, some teams move from designing prompts to learning prompts.

Now let me step back and summarize the whole slide.

As LLM systems become more useful, they usually stop being just prompts and start becoming architectures.

And once we say architecture, we are talking about tradeoffs.

Latency.

Cost.

Grounding.

Security.

Observability.

Evaluation.

Memory.

Tool use.

Reliability.

That is why this chart matters.

It helps us think about where a system belongs.

Not every problem needs agents.

Not every problem needs fine-tuning.

And not every application should move to the top-right.

In fact, many of the most useful real-world systems sit in the middle of the chart.

Especially around context, chaining, and RAG.

If I were to pause and ask you an architectural question, I would ask this.

If you were building an internal assistant that answers questions from company policy documents, where on this chart would you want to live?

The answer would probably be somewhere around contextual prompting, retrieval, and prompt pipelines.

Probably not full agents first.

Probably not prompt tuning first.

That is the right way to think about this image.

The goal is not to choose the fanciest architecture.

The goal is to choose the right architecture for the job.

Here are a few misconceptions I want you to avoid.

First, moving right does not always mean better.

It usually means more flexible, but also more complex and more expensive.

Second, agents are not the answer to every problem.

In many production systems, RAG plus carefully designed workflows is the better choice.

Third, prompt engineering is not just writing clever English instructions.

At production scale, prompt engineering becomes context engineering, retrieval design, orchestration, and evaluation.

Fourth, RAG does not automatically eliminate hallucinations.

It shifts the problem toward retrieval quality and source trustworthiness.

One more quick note about the logos on the slide.

Do not get too attached to the exact vendor names.

Tool landscapes change quickly.

Companies disappear.

Frameworks merge.

Platforms evolve.

What matters is not memorizing the logos.

What matters is understanding the architecture pattern each region represents.

The tools are temporary.

The patterns are durable.

And as we move upward and to the right on this chart, security and reliability also become more important.

Static prompts mostly need clarity.

Templates need input validation.

Contextual systems need careful context management.

RAG systems need strong retrieval quality and prompt-injection defenses.

Agents need guardrails, permissions, and clear action boundaries.

So architecture maturity also means operational maturity.

Let me close with a simple memory aid.

Levels 1 and 2 are about writing better prompts.

Levels 3, 4, and 5 are about building better workflows.

Level 6 is about grounding the system in real knowledge.

Level 7 is about delegation and autonomy.

Level 8 is about adapting the model itself.

If you remember that progression, you will be able to place almost any LLM application on this map.

And as builders, our goal is not to climb to the top-right because it looks advanced.

Our goal is to choose the right point on the map for the problem we are solving.
